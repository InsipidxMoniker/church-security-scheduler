# v1.0.3 feature amendment: qualifications and zone display labels

This amendment records the v1.0.3 qualification, zone label, scheduling and authentication changes. The [v1.2 specification](church_security_scheduler_mvp_spec_v1.2.md) remains the v1.0.0 baseline; this amendment supersedes only the rules listed here. Volunteer service-specific zone preferences remain a future roadmap item.

## Changed behavior

- Administrator-only settings `inside_zone_label` and `outside_zone_label` default
  to `Inside` and `Outside`. Each is trimmed, 1–100 characters, free of Cc/Cs
  control/surrogate characters, and distinct under trim/casefold. Explicit null
  is invalid; omission preserves the current value. HTML/PDF escape the labels.
  `settings_revision` checks all writes; label changes advance `config_epoch`.
- Zone identities and memberships stay fixed: outside = 1/2/3/8; inside = 4/5/6/7.
  Rotation and approvals use identities. No zone CRUD or remapping exists.
  Drafts retain their snapshots until explicit refresh with the displayed diff.
  Refresh never changes the date's timezone. Labels alone do not invalidate
  unchanged exact-pair/vacancy approvals, because no mapping or classification
  changed. The ordinary refresh revision/concurrency protections remain binding.
- `outside_available` replaces `restricted_qualified` exactly. It is required
  only for Positions 1/2. `rifle_qualified` is a boolean subset of Outside
  Available, enforced by API/service validation and a SQLite CHECK.
- Both staff roles may edit qualifications; volunteers cannot self-certify.
  New people default to both false. On edit an omitted rifle field preserves
  its current value. Removing Outside Available from a Rifle Qualified person
  is rejected: first clear Rifle Qualified and save, then remove Outside
  Available. There is no silent qualification loss or implicit confirmation.
- Qualification edits audit before/after values and advance `roster_epoch`.
  Removing Outside Available causes the existing hard draft eligibility conflict.
  Rifle-only changes leave legal assignments and approvals intact, mark prior
  optimization inputs outdated, and affect the next regeneration. In-flight
  generation/publication rejects stale epochs with 409.
- The new UTF-8 CSV header is `display_name,outside_available,rifle_qualified`,
  with literal `true`/`false` values. Legacy `display_name,restricted_qualified`
  remains supported and identified in preview; rifle defaults false. Errors or
  inconsistent pairs prevent any import. Duplicate previews, actor/epoch/expiry
  checks, atomic audit and separate PIN provisioning remain unchanged.
- Qualifications and rifle diagnostics remain staff-only. Public shared-link and
  own-response APIs omit them. Signal/PDF omit qualifications and diagnostics.
  New outputs include the snapshotted zone labels. Old payloads without label
  keys retain the former output representation and PDF column widths; rendering
  never consults live labels. No published row, hash or canonical payload is
  rewritten by the migration or label edits.

## Solver contract

Proven lexicographic sequence: **E > O > RS > RT > RP1 > B > U > original canonical tie-break**.
Each stage fixes the preceding optimal values; a stage starts only after its
predecessor is proven OPTIMAL. FEASIBLE/UNKNOWN retain the last valid incumbent
and stop lower priorities. RS counts services with a rifle assignment at 1/2
(0–2); RT counts those assignments (0–4). Per-service coverage uses binary
`covered_s <= r_s` and `r_s <= 2*covered_s`. Zero rifle coverage remains legal.
Rifle status never waives availability, eligibility, exclusivity, locks or rotation.

The additional **RP1** stage counts Rifle Qualified assignments at Position 1
(0–2). It follows optimal E/O/RS/RT and precedes B/U. With one assignable rifle in
a service, prefer Position 1 and use an eligible standard volunteer at Position 2.
Two rifles may occupy both positions; none are required. A valid standard-person
lock or intentional vacancy at Position 1 remains binding, so the rifle may use
Position 2. This is a soft preference and adds no qualification or approval rule.
Independent scoring, worker proof metadata, staff diagnostics and completion
checks all include RP1. Earlier six-stage metadata remains untouched and is
identified as historical, without turning legal assignments into conflicts.

The existing single **10-second total** model/solve deadline, single-worker CP-SAT
parameters, isolated subprocess, lifecycle kill deadline and process-wide
generation gate are unchanged. Result validation independently recomputes all seven
objectives, checks the ordered proof prefix/stage values, hard rules and epochs,
and requires all seven proofs plus completed canonicalization for OPTIMAL. The
original Sunday/UUID hash ranking and canonical candidate trials are unchanged.
Historical solver metadata stays historical and is labeled accordingly in review.

## Additional authentication form usability in the same v1.0.3 work

Only explicit HTML login submissions receive inline error pages; JSON Content-Type
or Accept takes precedence, and absent/wildcard/zero-quality HTML retains JSON
failures. Unknown user, wrong password and inactive user receive the same generic
401 alert on `login.html`. Keep only a bounded, escaped username without control
characters; never pass a password into template context. A fresh encrypted preauth
CSRF supports retry, including expired forms; authentication services and their
session issuance are unchanged. Login field/CSRF errors retain 422/403 and throttles
retain 429 plus Retry-After. Cross-origin requests still fail before authentication.

Invalid MFA/recovery submissions render `mfa.html` with 401 and empty code fields;
429 retains Retry-After. Revalidate the existing pending session before rendering
any authorized enrollment material; do not issue a new pending/staff session on
failure. Enrolled users see no seed/QR; initial enrollment retains its existing
private setup material. Expired pending sessions receive a fresh login form and
must complete password/MFA again. Auth POST responses vary on Accept. There is
no global conversion of API errors to HTML or new failure redirect policy.

Both refinements are included in v1.0.3 and schema 0006, with no additional migration or dependency change. The local Docker testing environment was updated and verified with these refinements.

## Migration and recovery

`0006_qualification_zones` is a forward-only transactional Alembic revision:

1. Native SQLite rename of `volunteers.restricted_qualified` to
   `outside_available`, retaining values, UUIDs, keys, indexes and references.
2. Add `rifle_qualified INTEGER NOT NULL DEFAULT 0` with CHECK enforcing boolean
   values and `rifle_qualified=0 OR outside_available=1`. Existing people do not
   become rifle qualified. No parallel legacy volunteer column remains.
3. Add the two default zone labels to settings. If a preexisting draft exists,
   increment settings revision/config epoch so it requires explicit refresh.
   Draft JSON, slots, locks, approvals and all publications stay untouched.

The fixed position metadata key `restricted_required` remains unchanged in the
positions table/snapshots; it describes the same immutable 1/2 mapping. This is
not a duplicate volunteer qualification field. Historical audits and payloads
retain their original vocabulary rather than being rewritten.

Use `operator migrate`, which first creates and integrity-checks a SQLite API
backup beside the database with mode 0600. Alembic executes under BEGIN IMMEDIATE
with transactional DDL. The interrupted-migration regression verifies that a fault
after rename rolls back all schema changes and preserves the pre-migration copy.
The populated rehearsal verifies all unaffected table rows, hashes, PIN hashes
and encrypted PIN records, staff credentials/MFA seed, availability, dates,
versions, locks, approvals, audit and publication pointers. Actual migrated SQLite
rejects inconsistent INSERT/UPDATE, nonboolean and null rifle values.

There is **no automatic downgrade**. Old application images cannot run against
schema 0006. Rollback requires a verified pre-migration backup, the original key,
matching old code/config and a clean isolated destination; changes since backup
are lost. Old-head backups must be verified/restored with matching old tools.
To recover into v1.0.3 instead, migrate an offline copy, then use the current
quarantined restore tool; retain the original backup. This path is tested.
Restore revokes sessions/links and closes collection, preserving publications.

Precise owner-approved upgrade commands and post-upgrade checks are in the
[README](../README.md#v102-to-v103). Never reset/bootstrap/init-key for an upgrade,
copy only a live DB file, delete WAL/SHM, use `down -v`, or overwrite an existing
restore destination. No production database or PBS configuration was touched.
